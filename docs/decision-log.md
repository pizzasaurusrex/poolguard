entries at the bottom; never rewrite an old one. If a later entry reverses an

This file is reference material, read on demand. Rules that apply to everyday

Spend stays proportional to validated progress.
- 2026-07-29: Software-first sequencing (ADR-010) — new hardware-free phase PD builds the pipeline on the dev machine (Ultralytics pose backend, video-file frame source, mock siren) before any hardware order; P0 narrows to Hailo validation. Inference is an explicit `PoseEstimator` protocol seam with Ultralytics (dev) and Hailo (Pi) backends.
- 2026-07-29: Work proceeds in reviewable PRs on feature branches against `main` — no direct commits to main for substantive changes.
- 2026-07-29: numpy promoted to a core dependency (Frame/pose seam types need it); cv2/ultralytics stay in the `vision` extra, and modules importing them live in files the core package never imports (`vision/video.py`, `vision/ultralytics_pose.py`) so protocol/model imports work without the extra.
- 2026-07-29: Frame images are enforced read-only (`ndarray.setflags(write=False)` in a validator) to extend the immutability rule to pixel data.
- 2026-07-30: Tracking = custom two-pass greedy-IoU tracker (`tracking.py`), not the `supervision` ByteTrack: ByteTrack's low-confidence rescue pass is kept (weak detections sustain tracks but never spawn them), Kalman motion model dropped (fixed camera, slow swimmers), and lost tracks are first-class output — a coasting track's `seconds_since_last_seen` is the submersion signal, which supervision's API doesn't expose. Association is strongest-IoU-first with one-to-one guards. Pure-function design: `advance(state, …) -> (new_state, people)`. `in_water` v0 = box center inside a config `pool_zone` rect.
- 2026-07-31: Regression suite ground truth is labeled per *shot*, not per clip — multi-shot clips are split at cut boundaries first (a cut teleports everyone in frame and forces new track IDs, inflating fragmentation metrics for non-tracker reasons). Splitting is done manually: ffmpeg `scene` scores proved unreliable on pool footage, where a splash scores like a cut and a cut between similar poolside shots scores low (thresholds 0.2/0.3/0.4 gave 7/2/2 cuts on the same clip).
- 2026-07-31: Labels live in a committed YAML manifest (`tests/labels/shots.yaml`, Pydantic-validated in `labels.py`) while footage stays gitignored — a shot whose file is absent locally *skips*, never fails, so a fresh checkout is green. Label granularity is shot-level verdict + onset window: firing late is a failure even when the verdict is right. PyYAML is a dev-only dep, so `labels.py` is never imported by the core pipeline (same isolation rule as the vision backends).
- 2026-07-31: Shot labels enforce strict both-or-neither on `expected_event`/`onset_window` — a verdict with no timing is a half-finished label that would pass even if the rule fired 40s late, which is not a save. Windows narrower than `MIN_ONSET_WINDOW_SECONDS` (0.1s) are rejected as typos: they assert frame-level precision a human eyeballing a clip can't deliver, and would fail the rules engine for annotation jitter rather than for being wrong.
- 2026-07-31: **Submersion is not detectable from a submerged-only clip.** First tracker run over the labeled library: the fully-submerged clip yields a 2% detection rate and *zero* tracks. The submersion rule works by a track existing and then coasting, so with no track ever spawned there is nothing to lose — no threshold value can rescue it. Submersion footage must show the person visible above water *first*, then going under. This makes a calm lead-in a hard requirement of the footage spec, not a nicety.
- 2026-07-31: Detection rate, not association, is the dominant tracker variable in the POC library (det% ranges 2–100%). ID-per-person churn correlates inversely with det%: intermittent detection makes a reappearing swimmer fail IoU against a stale box and spawn a fresh ID. Fix detection before tuning association. Caveat on the numbers: `max_coast_seconds` (30 s) exceeds every clip length, so no track ever expires and ID counts read closer to cumulative spawns than concurrent people.
- 2026-07-31: Found footage is cut for drama and always starts mid-event, so it cannot supply lead-in. Self-shot pool footage is promoted from a P2 nicety to the main PD gap.
- 2026-07-31: `submersion_timeout_seconds` 15.0 → 12.0, **provisional and fitted to footage**: every POC clip shows its event from frame one (no calm lead-in), so earliest-possible-fire equals the rule threshold and a clip can only test its rule if duration > threshold. At 15 s *no* clip could exercise submersion (longest is 13.8 s). 12 s buys one testable positive with 1.7 s of runway. This number came from clip lengths, not from safety analysis — re-derive on P1 footage against the false-alarm budget before it ships.
- 2026-07-31: Regression tests are opt-in behind a `regression` pytest marker (deselected by default via `addopts`) since they decode real video through a real pose model. `MAX_FRAGMENTATION` (track IDs ÷ real people) is an explicit tuning knob — loosening it is a regression that must be argued for in review.
- 2026-08-25: **Input resolution is the dominant detection variable, not the water.** On real 1080p footage from the backyard camera, `yolo11n-pose` detects in 0.0% of frames at `imgsz=640`, 66% at 1280, and 87% at 1920 — subjects are 35–100px tall, so the default 640 downscale destroys them before the model runs. This is the mechanism behind the 2–100% detection spread logged on 2026-07-31. Any deployment must run inference near native resolution.
- 2026-08-25: Tiled inference (overlapping crops at native scale) was benchmarked against full-frame upscaling and **rejected for now**. Aggregate numbers favored it (`tile4x2@512`: 93% vs 87% detection, 7.5 vs 6.4 fps), but visual verification showed the gain was mostly false positives: dappled tree shadow on deck pavers reads as person-shaped at small tile scale, plus duplicate boxes for one swimmer split across a tile seam. `detections/frame` is not a quality metric without ground-truth boxes — measure precision and recall before revisiting.
- 2026-08-25: Shadow false positives are a false-*alarm* mechanism, not just noise: a phantom detection on static shadow spawns a track, the track later stops being detected, coasts, and fires the submersion rule. Precision failures cost user trust; recall failures cost a save. Both are budgeted.
- 2026-08-25: Pool zone is a **polygon, not a rect**, and lives in a named `CameraProfile` in `tests/labels/shots.yaml` rather than on each `ShotLabel` — a fixed mount's geometry is declared once and referenced by name, so N clips from one camera don't duplicate 18 vertices. Shots with `camera: None` (all scraped footage) stay valid. The zone does two jobs: `crop_rect` (derived bounding box + margin) bounds inference for performance — 41% of frame, 59% of pixels skipped — while the polygon serves the `in_water` predicate, since this pool is kidney-shaped and its bounding box is ~a third deck.
- 2026-08-25: SimpliSafe integration **not built** — camera clips download as MP4 from the web UI, so no auth/proxy/RTSP work is needed for the POC. SimpliSafe exposes no RTSP/ONVIF; the cloud FLV endpoint (older cams) and LiveKit/WebRTC (Outdoor Cam) exist but were scoped out as unnecessary. Motion-gated live streaming was considered for a zero-hardware POC and left open pending a measurement of stream session duration and re-trigger behavior.
- 2026-10-11: Alert channels live in an `alerts/` package, one module per channel. ntfy (`alerts/ntfy.py`) splits a pure `build_message(SafetyEvent) -> NtfyMessage` from an `NtfyNotifier` that takes an injected `httpx.Client`, so message content is tested without a network and delivery is tested against `httpx.MockTransport`. httpx added as a core dependency for this. `ntfy_topic_url` is a `SecretStr` because the topic name is the only credential; delivery errors are raised `from None` since httpx embeds the request URL in its exception text.
- 2026-10-11: PoolGuard gets its own ntfy topic, separate from the homecast monitoring topic, so pool alerts are not mixed with infrastructure noise and can carry their own notification settings. The topic is supplied only via `POOLGUARD_ALERT_NTFY_TOPIC_URL` (repo is public).
- 2026-10-11: Pipeline liveness is reported through an Uptime Kuma push monitor on the homecast Pi (`alerts/heartbeat.py`). The pipeline pings; Kuma alerts when pings stop, so a crashed or hung detector is noticed without its cooperation. A failed ping raises `HeartbeatError` for the caller to log and continue: a monitoring outage must never stop detection. This is a health check with minutes of lag and an internet dependency, not an emergency channel.
- 2026-10-11: Every settings section declares `env_file=".env"` and `extra="ignore"` itself (shared `_SECTION_CONFIG`). An env file declared only on the top-level `Settings` was never read by the nested sections, since each is its own `BaseSettings`: real env vars worked, `.env` silently did not. Same family as the 2026-07-24 nesting bug.
- 2026-10-11: `poolguard-alert-test` sends one real notification through each configured alert channel and exits non-zero on failure. It loads `AlertSettings` alone so it runs without a camera configured.
- 2026-10-11: **SimpliSafe live stream measured: no session cutoff found in ~47 min; battery drain still unmeasured.** The Back Yard Outdoor Cam's web live view (LiveKit/WebRTC, one `live-view` API call then a WebSocket to `livestream.services.simplisafe.com:7880`) connected in ~2.7 s at 1920x1080 and ran at least 47 min with no stall, drop or "still watching?" prompt; the only event was an in-place track renegotiation at 43:25. The camera then died of a flat battery somewhere between 47:28 and 51:50. That is not evidence about drain rate: the low-battery warning had already been showing for a day or more before the test, so the run started near empty. Unknown: runtime from a full charge, any session cap beyond ~50 min, and whether a dropped session restarts without a click (the camera died before that could be tested). Re-run from a full charge, noting battery % at start and end, before deciding whether live streaming is viable as a test-phase source. No frames were pulled into the pipeline — that would need an unofficial LiveKit client or browser capture, and stays unbuilt.
- 2026-10-11: SimpliSafe frame capture, if built, goes through LiveKit's Python SDK (`livekit`, a direct headless client) rather than a headless browser or screen capture — lighter, no display needed, and it fits the existing `FrameSource` seam. Chosen over Playwright, which stays the fallback. Bench-only, same status as the Nest Cam under ADR-002: it rides SimpliSafe's private API and is never the production camera. **Unverified and gating any code:** that the `live-view` response actually carries a LiveKit URL and token, and how to obtain a SimpliSafe access token headlessly (`simplisafe-python` is the lead; a code search found no existing LiveKit support in it). The dependency would live in its own extra, in a module the core package never imports.
- 2026-10-11: CI added as a single GitHub Actions workflow (`.github/workflows/ci.yml`) running `uv sync --locked`, `ruff check`, `ruff format --check` and `pytest` on every PR and on pushes to `main`. Before this nothing ran on GitHub: checks were local only and `protect-main` required a PR but no status check. Actions are pinned to commit SHAs (the repo is public, and `setup-uv` no longer publishes moving major tags). CI installs **without** the `vision` extra, since ultralytics pulls in torch and would turn a ~30 s job into a multi-GB install; the cost is that the four cv2/ultralytics test modules (`test_hud`, `test_render`, `test_ultralytics_pose`, `test_video_source`, 29 tests) skip in CI and still depend on a local run. Measured on a clean env: 97 passed, 4 skipped, 27 deselected without the extra, against 126 passed with it. The regression suite stays local too (footage and weights are not committed).
- 2026-10-12: Two inputs that used to stop the pipeline with a `ValidationError` are now absorbed. A clock that steps backwards (NTP correction on a live source) gave a negative `seconds_since_last_seen`; the tracker now clamps unseen time at 0, reading the track as just seen. A NaN or infinite box or confidence from the model is dropped in `detections_from_arrays`, like a degenerate box. Chosen over raising because a crashed detector misses everything, and a missed detection is the worse failure. Not addressed: a large backward step also delays coasting expiry and the submersion clock by the size of the step; a monotonic clock for the live source is the proper fix when the live loop is built.
- 2026-10-12: PyYAML gets its own `labels` extra (it stays in the dev group for tests). `vision/render.py` imported `labels.py` at module level only for a type annotation, so `poolguard-replay --render` crashed with `ModuleNotFoundError: yaml` on any install without the dev group. The import is now `TYPE_CHECKING`-only, and `--labels` without PyYAML exits with the install hint. Follows the standing rule that a new optional dependency gets its own extra.
- 2026-10-12: The pose estimator's confidence floor now defaults to the tracker's `low_confidence` (0.1), down from 0.25. At 0.25 the estimator discarded detections in the 0.1–0.25 range before the tracker saw them, so the bottom of the rescue band was unreachable. `poolguard-replay` and the regression fixture take the floor from `TrackingSettings.low_confidence`; `--min-confidence` still overrides. Measured on the local regression suite: the same 4 failures before and after (`fullySubmerged_08` finds nobody; `activedrowning_01`, `childFallsIn_03` and `distress_05` fragment, `distress_05` at 5 IDs for 1 person), so the floor alone does not change any pass/fail result on this library.
- 2026-10-12: `UltralyticsPoseEstimator` now sets `imgsz` per frame instead of leaving the Ultralytics default of 640, which the 2026-08-25 entry showed detects nobody on the 1080p backyard footage but which the code never acted on. `inference_size` takes the frame's longest side, rounds it up to a multiple of the model stride (32) and caps it at `max_inference_size` (default 1920, `--max-inference-size` on the CLI). Derived from the frame rather than fixed in config so a smaller source is not upscaled for no gain. Measured on the local regression suite, on top of the 0.1 confidence floor: failures drop from 4 to 2. `fullySubmerged_08` now finds its person and `childFallsIn_03` no longer fragments; `activedrowning_01` and `distress_05` still fragment (`distress_05` at 4 IDs for 1 person, down from 5). Speed was not re-measured; the 2026-08-25 figure for 1920 was 6.4 fps on the dev machine.
- 2026-10-12: Tracker gains a containment pass between the IoU pass and the rescue pass. Traced on the two clips still failing fragmentation: neither ever has two confident detections in one frame, so the extra IDs are not duplicates. The model's box for one swimmer flips between head-only and whole-body (for example 0.14x0.21 then 0.50x0.20 at the same spot), which scores IoU 0.2 or so against a 0.3 threshold and spawned a new ID. An unmatched high-confidence detection now keeps the ID of a track when `containment` (share of the smaller box inside the larger) is at least `containment_min` (0.7). Only tracks seen within `containment_window_seconds` (1.0) are eligible: the window is the safety limit, so a newcomer's large box cannot adopt a person who has been under for longer and reset their unseen clock. A track that matched its own detection by IoU is never taken. Measured on the local regression suite: failures 2 to 1; `distress_05` 4 IDs to 2 (passes), `activedrowning_01` 4 to 3 (still fails at ratio 3.0), the six-person clip stays at 7 IDs for 6 people. **Not tuned to pass the last clip.** Its remaining spawns need containment 0.49 or a 2.5 s window, and loosening either to fit one clip trades away the safety limit. That clip has a confident detection in only 15 of 113 frames, so it is a detection-rate problem, in line with the 2026-07-31 finding. `MAX_FRAGMENTATION` is unchanged.
- 2026-10-12: `TrackingSettings.pool_zone` changes from a rectangle `(x, y, width, height)` to a polygon of normalized vertices, and `in_water` is now a point-in-polygon test on the box centre. This completes the 2026-08-25 decision, which put the polygon in `CameraProfile` but left the tracker on the rectangle, so the kidney-shaped pool's deck still counted as water. Geometry lives in a new dependency-free `geometry.py` (ray casting, shoelace area, one `validate_polygon`) shared by settings and `labels.py`; a zone with fewer than 3 vertices, a vertex outside the frame, or no area is rejected. `poolguard-replay --labels` now applies the shot's camera profile polygon as the pool zone, which gives `camera_for` its first real caller. **Breaking for config:** `POOLGUARD_TRACKING_POOL_ZONE` is now a JSON list of `[x, y]` pairs; the default is still the whole frame. Not done: `crop_rect` is still unused (inference runs on the full frame), and nothing asserts `in_water` on real footage yet.
- 2026-10-12: First run on real backyard footage (five 1080p, 20 fps clips from the SimpliSafe mount, 13 to 21 s each), with native-resolution inference and the polygon zone. A detection in 95 to 99% of frames per clip (216/228 to 316/320), at about 5.9 fps on the dev machine. Seen in sampled frames, not a full review: people on the deck and upright in the water are boxed; swimmers low in the water or at the pool wall drop out for stretches; one clip grows a phantom track on shadowed deck pavers that coasts past the submersion timeout. Track IDs per clip were 3 to 8 for about 3 people, a mix of phantom tracks and ID changes that has not been separated.
- 2026-10-12: The backyard `water_polygon` is re-traced from that footage and is now generated, not hand-drawn: median frame across the clips (removes swimmers), HSV water-colour mask, largest contour, simplified to 35 vertices. The hand-traced polygon drifted from the waterline, worst along the near edge, where it cut through the water. Known limit that the trace does not fix: `in_water` tests the box centre, and from this elevated angle a person standing on the near coping projects up over the water, so their box centre can land inside the polygon.

Their labels in `tests/labels/shots.yaml` now point at footage that no longer exists and skip in the regression suite; they are to be replaced by labels for the backyard clips. - 2026-10-13: Regression suite run against the five labeled backyard clips (all 3 people, all labeled quiet): tracker finds everyone in every clip; two clips fail fragmentation, `jump-in` (7 IDs) and `swimmer-mostly-hidden` (8 IDs) against a limit of 6 for 3 people. Not separated yet: how many of those extra IDs are phantom deck tracks and how many are real ID changes.
- 2026-10-13: Rules engine v0 lands with the submersion rule only (`rules.py`). Same shape as the tracker: a pure `evaluate(state, people, now, mode, settings) -> (new_state, events)`. A person whose track was last seen in the water and has been unseen for `submersion_timeout_seconds` raises one `SUBMERSION` event at the emergency tier. Events are edge-triggered (once per incident; the state is the set of tracks currently past the threshold, so resurfacing or track expiry re-arms the rule) because the alert manager should not have to de-duplicate per-frame repeats. Maintenance mode raises nothing and clears that state, so an incident still in progress when the pause ends is raised. Built now, before tracking is clean, so that false alarms become a number per clip; distress is deferred until there are several real examples to derive it from. The replay loop always runs the rules after the tracker, with the mode taken from `RulesSettings.default_mode`.
- 2026-10-13: Regression suite gains event assertions: a quiet shot must raise nothing, and a positive must raise its labeled event inside the onset window. Each shot is now replayed once per run and shared by its tests (4 min 20 s for five clips, down from over 14 min when each test replayed its own). Shots with a camera profile are replayed with that profile's polygon as the pool zone. First result on the backyard clips: no clip raises a submersion event, which matches their labels but proves little, since at 13 to 21 s none leaves room for a 12 s timeout to matter. A positive needs footage that keeps recording at least 15 s after the swimmer goes under.
- 2026-10-13: **First true positive on real footage.** `drowning-test.mp4` (40 s, one swimmer, under from about 25 s): the submersion rule fired at 37.0 s, 12.0 s after the swimmer was last seen. The same clip raised two wrong events. (1) A false alarm at 13.5 s: the swimmer is first tracked standing at the pool edge, jumps in, and is picked up in the water as a new ID; the standing box is left as a ghost that counts as in the water and times out. Any jump-in can do this, so it is a systematic false-alarm path, not a one-off. (2) A duplicate at 37.0 s: two tracks sat on the one swimmer from about 20 s and expired together. The clip averages 19.3 fps while the file source assumes a constant rate, so pipeline times drift about a second from player times.
- 2026-10-13: **The pool zone goes stale whenever the camera is re-mounted** ([#23](https://github.com/pizzasaurusrex/poolguard/issues/23)). The camera is battery powered, comes down to charge, and does not return to the same angle. `drowning-test.mp4` was recorded after a re-mount and the `backyard_simplisafe` polygon, traced for the previous angle, cuts across the patio in it; the rule fired there only because the stale outline happened to overlap the pool. A stale outline can cause both a missed submersion and a false alarm, and nothing detects it. No fix chosen; options are in the issue (power the camera in place, re-trace automatically, detect and correct the shift, raise `SYSTEM_DEGRADED`). Until then every camera angle needs its own profile, and results from the re-mounted clip are not a valid test of `in_water`.
